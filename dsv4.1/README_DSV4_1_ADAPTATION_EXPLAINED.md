# 用白话理解 DeepSeek V4.1 的 UCM 适配

## 这份文档怎么读

这份文档不按 commit 顺序讲，也不要求你先看懂代码。我们按照“服务启动 → 第一次计算并保存 → 第二次命中并恢复 → 接着计算”的顺序，把修改的理由串起来。

你读完后应该能回答三个问题：旧办法为什么不够用？现在具体换成了什么办法？为什么这样改能解决对应的问题？

代码范围与前两份说明相同：`dsv4.1` 分支截至 `7a750180` 的改动，包含 `9da6f1d0`。不是当前 `step_wise` 分支的说明，也不是对所有后续 vLLM 版本的兼容性承诺。

需要看实现时，可以对照 [详细代码版](README_DSV4_1_ADAPTATION_DETAILED.md)；需要串讲提纲时，可以看 [概览版](README_DSV4_1_ADAPTATION.md)。这里的小数字例子用于解释机制，不代表每个镜像的实际配置都一样。

## 1. 先想清楚：我们到底要恢复什么？

模型读完一段输入后，会留下后面计算需要用到的中间结果。KV cache 就是其中很重要的一部分。

你可以把它理解为“前面已经做过的计算笔记”。下一次遇到相同前缀，如果能找回这些笔记，就不必完全从头再算。

UCM 做的事情大致是：

```text
第一次：输入 → 模型计算 → GPU 上产生缓存 → UCM 保存到外部
第二次：相同前缀 → UCM 找到缓存 → 放回 GPU → 模型从合适位置继续算
```

这里“合适位置”非常关键。保存了多少数据、放回了哪里、模型准备从哪里继续，这三件事必须对得上。

举个例子：你保存的是“算完前 256 个 token 后的状态”，但恢复后却让模型按“只算完前 255 个 token 的状态”继续运行。即使复制的字节一个都没错，某些状态也可能已经超前了一步。

所以我们的目标不是“命中率高”，也不是“没有报错”，而是：**恢复以后，模型拿到继续计算所需的正确状态，效果应当与正常计算这段前缀相当。**

这不等于所有运行条件下输出文本都必须逐字相同。采样和数值差异也会影响输出；这里首先要保证的是恢复的数据和计算进度正确，不能因为外部缓存破坏模型精度。

## 2. 为什么 V4 能用的办法，到 V4.1 还要改？

不是因为 UCM 要重新实现一遍 V4.1，而是因为“模型留下的笔记怎么组织”变了。

这次需要处理的变化主要有：

- 多个模型层可能使用同一份 KV 或 Indexer 缓存。Indexer 可以先理解为帮助注意力筛选位置的索引相关缓存，它的数据也要正确恢复。
- 一个实际保存的状态，可能对应多个逻辑 token。
- 有的组保存可复用结果，有的组只是计算过程中的临时工作区。
- 新版 vLLM 描述物理内存的方式变了，数据、量化信息和空隙不一定按旧办法排列。
- 新版恢复流程可能要把命中前缀的末尾重新计算一小段，也就是 replay。

因此，“知道模型有多少层，再套旧公式算每条缓存有多大”已经不够了。

还要特别区分：**跨层共享，不是每隔若干 token 才更新一次缓存。**

“10 个层共用一份”说的是不同层之间谁使用哪份缓存；“10 个 step 更新一次”说的是时间上的更新频率，这是两回事。我们的改动没有写死“每 10 层搬一次”，也没有写死“每 10 步搬一次”。

UCM 仍然负责存取，模型和 vLLM 仍然负责计算、共享关系及缓存分配。适配的关键，是正确读取 vLLM 给出的缓存信息。

## 3. 启动时第一件事：让 V4.1 进入正确的 Connector

### 旧做法哪里不合适？

以前入口会先尝试检查“这是不是 HLA 布局”，然后才决定是否使用 FAWA。

问题是：你最后不使用 HLA，也不代表前面的 HLA 检查一定安全。它可能已经读取了新布局里不存在的字段，或者用不适用的规则理解了 V4.1 的临时组。

就像你最终要走甲通道，却被要求先按乙通道的表格填一次资料；如果乙的表格与你不兼容，在到达甲之前就出问题了。

### 改成什么？为什么有效？

先判断是否属于 FAWA。属于，就直接交给 FAWA，不再进行 HLA 布局探测。

这里的关系是：V4.1 在这套实现中走 HMA 路径，具体处理者是 `UCMFAWAConnector`，不是 HLA Connector。此次改的是公共入口的选择顺序，并没有在 `hla_connector.py` 里实现 V4.1。

这样做消除了“不该经过的检查”。之后再根据共享来源字段、压缩配置等特征，决定启用哪些 V4.1 专用处理。

对应代码：`UCMConnector.__init__`、`UCMFAWAConnector._init_group_metas`。

## 4. 第二件事：弄清真正要保存的东西有哪些

### 先别把“模型层”和“缓存组”当成同一个东西

一个模型层可能涉及不止一种缓存；不同模型层也可能共享缓存。缓存组则是 vLLM 管理这些缓存的一种组织方式，不等于模型层数。

因此，组变多，不代表独立缓存一定变多；模型层数不变，也不代表要搬的字节数不变。

### 改成什么？

UCM 不再用 V4 的固定层数公式估算 V4.1，而是逐组读取 vLLM 提供的层名、每层缓存说明和真实张量。

可以理解为：以前依赖“我记得这种模型应该有这些东西”，现在改为“你实际登记了哪些东西，我就按这些东西计算”。

这不是 UCM 自己发现任意两个地址相同就自动去重。共享关系仍依赖 vLLM 正确表达，UCM 据此建立搬运计划。

### 再把这些东西分成两类

第一类是可以保存并恢复的结果；第二类是不能按普通前缀缓存直接复用、应由后续计算重建的状态。

代码通过 `prefix_cacheable` 和 `enable_kv_transfer` 等属性判断，不是看到名字像 ring、SWA 就一律跳过。

这点很重要：**临时状态不存，不等于临时状态没用。** 它仍然要在正确的恢复边界或 replay 过程中被重建。只删掉传输、不处理恢复过程，当然不够。

### 不存的组，为什么还要留着编号？

假设 vLLM 给出的顺序是：

```text
第 0 组：要保存
第 1 组：不保存
第 2 组：要保存
```

UCM 传给后面的列表仍应保留中间的空位置，不能删掉第 1 组后，把原来的第 2 组当成新的第 1 组。

否则后面按组号找 GPU 地址时，会把数据放到别的组里。我们保留组编号和占位信息，只跳过它的实际传输，解决的就是这种错位。

对应代码：`_init_group_metas`、`register_kv_caches`、`_slice_group_block_ids`。

## 5. 第三件事：分清“覆盖多少 token”和“实际有多少条状态”

假设某个 block 覆盖 64 个逻辑 token。

对一种缓存来说，每个 token 对应一条状态，那么实际保存 64 条。对另一种缓存来说，每两个 token 对应一条状态，那么实际只有 32 条。

两者都覆盖 64 token，但并不是一样多的数据。

这里的“两个 token 对应一条状态”只是数量关系，不表示 UCM 把两个 token 的数值简单取平均。如何生成状态是模型的事情，UCM 只负责按已知比例定位和搬运。

### 旧办法会错在哪里？

如果把张量里的“状态条数”当成“token 数”，你以为向后移动 32 个 token 就要移动 32 条状态。

但对于两个 token 一条状态的缓存，正确答案应该是移动 16 条。起点一错，后面的数据就全错位了。

### 修改为什么有效？

UCM 读取每层的 `tokens_per_state`，分别换算状态条数、起始偏移和复制长度。即使同一个组里的不同层采用不同压缩比例，也分别计算，不共用一个猜出来的偏移。

所以这处修改不只是“少搬一点数据”，而是让“这段逻辑前缀”准确对应到“这段物理内存”。

对应代码：`_group_tokens_per_state_by_layer`、`KVCacheGroupLayout` 的地址与长度计算。

### 顺便解释：为什么每 token 的 KV 变小，不一定要把 block size 改大？

这里容易把三种大小混在一起：

- block size：一块覆盖多少逻辑 token。
- 物理页大小：GPU 上实际为某段缓存安排多少字节，可能带空隙。
- 外部文件大小：一条存储记录占多少字节，还可能需要 4 KB 对齐。

“每 token 更小，所以要增大 token 数才能填满固定页”只有在页容量固定、组组成不变、布局不变等前提下才成立。V4.1 和新 layout 恰恰改变了这些前提。

因此这次适配不根据一个反比关系猜 64 或 256，而是读取 vLLM 给出的组、布局和对齐要求。它解释了为什么旧推导不能直接套用，但不能单凭这些 UCM 改动证明某个硬件上 64 一定性能最好。

## 6. 第四件事：知道数据在内存里到底怎么摆

前面解决的是“有多少数据”，这里解决的是“数据在哪里”。

`layout` 说白了，就是内存中的摆放方式。张量显示的 shape 只是一部分信息，不能代替真实的地址和间隔。

### 6.1 数值和 scale 都要恢复

量化缓存不只有数值本身，还需要解释这些量化数值的缩放信息，也就是 scale。

你可以把它理解为“数字和配套的刻度”。只保存数字、把刻度漏掉或配错，复制过程可能完全不报错，但模型使用时得到的数值含义就变了。

在适配的一类 packed 布局中，内存更像这样：

```text
一整段 value 数据 | 一整段 scale 数据
```

而不是必然这样：

```text
第 1 条 value + scale | 第 2 条 value + scale | ……
```

举例：每条状态总计 584 字节，其中 value 576 字节、scale 8 字节。这只能说明总量，不能说明每条状态的两部分一定紧挨着。

如果实际有 32 条状态，要取后半段，就必须分别找到后 16 条 value 和后 16 条 scale。不能简单从整页中间开始，连续搬走一半就认为正确。

所以分段路径新增了两份地址和长度描述：一份指向 value，一份指向 scale。主 KV 和 Indexer 的格式分别识别。

它能解决问题的原因很直接：保存与恢复时，数值和解释数值所需的信息都按真实位置对应起来了。

### 6.2 新布局为什么又选择整页搬运？

新版 vLLM 还会给出更完整的物理位置说明，也就是 placement。它说明每层的页占多大空间、相邻 block 间隔多远等信息。

其中可能有 padding，可以先理解为为了布局或对齐留下的空隙。比如有效数据占 100 个单位，但这一层的页实际占 112 个单位，那么找到下一段的位置时，就不能只加 100。

在这条新路径中，我们按完整的 layer page 搬运，包括其中的空隙；起点与跨 block 间隔从真实张量读取，整页大小从 placement 读取。

好处不是“空隙里的内容对模型有用”，而是恢复时保留这一整段内存的原有组织，不再根据表面 shape 猜该怎么切分。

为了让这个办法成立，代码禁止从页中间开始搬，也禁止只搬半页，同时检查 shape、状态数和步长是否符合当前支持范围。

### 6.3 为什么搬运粒度也要跟着变？

假设 vLLM 允许以 32 token 为单位做前缀匹配，但实际完整页覆盖 64 token。

分段路径能正确描述半页时，可以用 32 token 的粒度；整页路径既然规定不能只搬半页，就要使用能覆盖完整页的对齐粒度。

所以代码从 vLLM 读取两种粒度：分段时取 hash 粒度，整页时取 scheduler 对齐粒度，而不是继续沿用固定常量。

这是“选中的前缀长度”和“实际能安全搬运的内存单位”必须一致的问题。

对应代码：`_group_physical_layout_by_layer`、`_v41_whole_page_sizes`、`KVCacheGroupLayout._build_layout`、`_init_group_metas`。

## 7. 第五件事：保存前，两边先把大小和格式对上

先认识两个角色：scheduler 决定哪些请求、哪些 token 应该处理；worker 接触实际设备张量，执行计算和搬运。

为了让保存和查找一致，它们必须对“一条外部缓存记录是什么”有相同理解。

### 7.1 两边算出来的字节数必须相同

scheduler 根据缓存说明计算文件应该多大；worker 根据实际布局计算真正要搬多少字节。

旧 V4 有固定公式，V4.1 改成按实际组、层、压缩比例和页大小求和，再做外部存储需要的 4 KB 对齐。

如果两边最后对不齐，就直接报错。这样可以防止用错误大小继续保存，直到后面模型精度下降才暴露问题。

同时要分清：GPU 页内的空隙，和外部文件补齐到 4 KB，不是同一回事。文件大小对齐了，不代表页内地址就自动正确。

### 7.2 算对了，还得保证 Store 真正用它

旧配置可能有一个 `tensor_size`，意思是按一个统一大小处理。

但现在不同层、不同分段需要不同大小，所以要使用 `tensor_size_list`。如果旧的单值配置优先级更高，就会把前面算好的列表盖掉。

因此 V4.1 路径移除旧单值，确保 Store 按列表搬运。这解决的是“上层算对了，下层却没按这个结果执行”的问题。

### 7.3 格式变了，缓存的标识也必须变

相同模型、相同输入，不代表不同版本保存出来的缓存字节格式相同。

因此我们给缓存 key 的命名空间加入 dtype、block size、压缩配置、组组成、replay 设置和物理布局等信息。你可以把它理解为：除了记录“这是谁的笔记”，还记录“这份笔记采用哪种格式”。

格式不同，就不能拿来直接互换。这样旧文件可以继续留在目录里，但新格式不会把它误认为自己的记录。这不是自动迁移旧数据。

还有一个反方向的问题：两边明明是同一种物理格式，却因为 scheduler 合并了缓存说明、worker 保留了逐层说明，而生成了不同 key。

这会表现为“保存了，但下次总找不到”。有 placement 时，我们用两边一致的物理布局信息识别格式，避免把两种表达方式误认为两种格式；初始化时也重新绑定相应的 hasher。

对应代码：`_derive_v41_file_sizes`、`_create_store`、`RequestHasher` 和 FAWA 初始化。

## 8. 第一次请求：到底保存哪些内容？

现在准备工作完成了。第一次请求没有外部缓存，就正常计算，再按前面建立的地址和长度描述保存结果。写到外部通常叫 dump；从外部读回叫 load。

FAWA 原有存取方式大体保留下来，只是里面的数据组成和边界适配了 V4.1：

- FA 保存连续前缀对应的缓存，恢复时要有前面相应的连续记录。
- 如果存在需要保存的窗口组，WA 保存某个边界处的窗口尾部快照，恢复时取最终命中边界的那一份。
- 被排除传输的组不写入外部，交给正确的恢复计算处理。

可以把 FA 理解成“需要保留的前缀结果”，把 WA 理解成“在这个边界继续工作时，窗口里应当留下的状态”。

### 没有 WA Store，为什么仍然可能是正常的？

在新版配置中，窗口状态可能被标记为不传输，由 replay 重建。此时没有持久化窗口组，就不应该为了满足旧流程硬建一个 WA Store。

但这必须一起修改：创建时不建 WA，保存时不写 WA，查找时不要求 WA 文件，加载时也不读 WA，相关预取操作同样跳过。

否则只改其中一步，就可能出现“FA 保存完了，但因为没有 WA，永远判成不能用”。这就是 FA-only 适配的意义。

这也说明，不能只根据 V4.1 比 V4 的缓存少，就推导 load/dump 调用一定减少多少次。传输字节数、FA/WA 是否存在、每步新增完整块数、请求调度，都会影响实际工作量。

对应代码：`_create_wa_store`、`wait_for_save`、`_lookup_external_hit_blocks`、`start_load_kv`。

## 9. 第二次请求：找到文件以后，为什么还不能立刻全用？

命中说明“找到了对应记录”，还要检查“能不能从这个边界安全恢复”。

### 9.1 不能从压缩组中间随便开始

假设两个 token 才形成一组状态，那么恢复位置至少要落在相应边界上。否则接下来可能需要半组之前的临时状态，而那份状态并没有保存。

因此代码检查各组的压缩要求，保证外部缓存的逻辑块边界满足恢复对齐。

这就是为什么“文件存在”只是条件之一，不是可以任意截取命中长度的许可。

### 9.2 为什么完整命中时，要留最后一个完整块计算？

模型还需要执行计算来产生后续输出。但不能一边加载“算完这个块后的状态”，一边又退回这个块里面计算最后一个 token。

特别是存在窗口快照、临时压缩状态时，退回一步并不等于简单把一个计数器减 1。

因此这里采用更明确的办法：在选择可命中的块时，就预留最后一个完整块。

以外部记录粒度为 64 token、暂不考虑 replay 等其他限制为例：

- 输入正好 256 token，候选最多用前 192 token，最后 64 token 重新计算。
- 输入为 257 token，则前 256 token 都可以作为候选，剩下 1 token 计算。

这不是随意降低命中率，而是在保证加载状态与继续位置相容的前提下复用。实际命中还要受存储记录、阈值等条件限制。

### 9.3 很短的窗口快照，也不能索引到别处

如果前缀还很短，窗口需要的块数可能超过现有块数。旧索引算出负数时，可能意外读到数组尾部，而不是“前面不存在的数据”。

修改把这种下界裁到首块，用重复首块填充固定形状的快照；真正超过已分配范围的情况则报错。这里填充的是存储表示，并不是让模型把虚构 token 当作历史输入。

对应代码：`get_num_new_matched_tokens`、`_slice_group_block_ids`。

## 10. 真正往 GPU 写回前，还要挡住一个精度问题

这是之前“第一次正常、外部命中后精度下降”那个问题中非常重要的一处修改。

### 10.1 CPU 上的调用顺序，不代表设备操作已经完成

设备操作可能是异步提交的。前面的 Python 函数返回了，只能说明工作提交出去，不一定说明 GPU 已经执行完。

如果原执行流上还有针对缓存页的初始化、清零或其他写操作，而外部加载又从另一个执行流往这块内存写 KV，两者没有明确先后关系，就可能发生覆盖。

错误时序可以这样理解：

```text
旧写操作还在排队 → 外部 KV 已经写回 → 旧写操作才执行，把 KV 改掉
```

文件是对的，地址也可能是对的，H2D 复制也完成了，但模型最后读到的数据已经不是刚才加载的那份。

### 10.2 为什么原来“等 load 完成”还不够？

等 load 完成，保证的是“我搬完了”。它不能保证“之前排队的其他写操作早就结束，不会在我之后覆盖”。

所以需要两个方向的保证：搬运前，旧写操作结束；搬运后，加载完成才能使用。

修改后的顺序是：

```text
设备同步，等此前工作结束 → 外部 KV 写回 → 等加载完成 → 模型继续计算
```

这次使用的是 `device.synchronize()`，而且只加在 V4.1 有外部加载任务的路径上。

### 10.3 为什么没 error、没乱码，分数仍可能大幅下降？

因为读写可能都在合法地址里，系统不知道这些合法字节在语义上已经错了。模型也往往仍然能生成流畅语言，只是使用了错误的上下文状态。

所以命中率高只能证明大量记录被找到，不能证明恢复后内容正确。ARC 得分也不会与命中率建立简单的线性关系，不能据此计算“命中多少就应该只掉多少分”。

此前你反馈添加同步后问题解决，这支持该修复对已复现场景有效。但本文没有新的设备 trace，不把具体哪个 kernel 覆盖了哪段地址当作重新实测的事实。

### 10.4 为什么不顺便说其他模型肯定不会有问题？

其他模型可能没有触发同样的写入路径或时序，但不能仅凭“以前没遇到”证明永远安全。本次只是把新增同步限制在已经需要它的 V4.1 路径，保留其他模型原有行为。

这个办法也有代价：设备同步比较强，可能减少计算与搬运重叠。它首先解决正确性；将来如果要提高并行度，需要更精确的事件依赖，不能单纯删掉同步。

对应代码：`start_load_kv`，其后仍有 `_wait_all_load_task` 等待加载完成。

## 11. 加载完成后，为什么新版还要 replay？

回到第 4 节：我们没有保存所有临时工作状态。

那模型接下来怎么继续？一种恢复办法是利用已经恢复的持久化缓存，把前缀末尾的一段重新计算，让临时工作区重新形成正确状态。这就是这里的 replay。

因此，命中 256 token 不一定等于可以直接从第 257 个 token 开始实际执行；调度器可能要求先回到更早的位置补算一段。

这不是 UCM 自己重新实现模型计算。vLLM 和模型负责 replay，UCM 要读取 `prefix_replay_tokens` 并尊重调度器给出的实际进度。

### 为什么有些小命中要放弃？

如果命中的 token 全部落在必须 replay 的范围里，最后还是要全部重算，就不能把它当作有效复用前缀报告出去。

### 为什么这能和“不保存临时组”配合起来？

因为恢复方案不是“只恢复一部分，然后假装已经全部恢复”，而是“持久化部分从外部加载，未保存的部分按模型要求重建”。

这依赖 vLLM 的恢复语义和实际执行。UCM 做的事情，是不去传输被排除的组，同时正确配合命中边界和 replay 进度。只有这几部分配合，省掉临时组传输才是安全的。

对应代码：`_init_group_metas`、`get_num_new_matched_tokens`、`build_connector_meta`。

## 12. replay 时还有一个坑：不能把没算出来的东西提前存了

这是比较隐蔽但很关键的一处修改。

假设外部命中 256 token，要 replay 其中末尾的 128 token，每一步实际执行 64 token。

当前真实进度应当是：

```text
从 128 算到 192 → 从 192 算到 256 → 从 256 算到 320
```

前两步是在补算已命中前缀内的状态，第三步才产生超过原命中边界的新结果。

如果 UCM 错把“外部命中 256”当成“本步从 256 开始计算”，第一步就会认为已经完成到 320，并计划保存 256 到 320 的数据。

实际只计算到 192，后面那段还没产生。把它保存出去，就会制造一份以后能命中、但内容错误的缓存。

### 改成什么？为什么有效？

构建 dump 计划时，replay 路径使用 scheduler 提供的实际 `num_computed_tokens`，而不是把命中长度当作本步计算起点。

于是：

- 算到 192：不保存原命中边界之后的新块。
- 算到 256：仍没有越过原命中边界。
- 算到 320：才保存新完成的 256 到 320。

这里“实际进度”与“命中长度”是两个量。分开以后，外部存储不会因为 replay 而提前收到未完成的数据。

对应代码：`build_connector_meta` 向 `_generate_dispatch_meta` 传入 `computed_tokens`。

## 13. 把整件事重新串起来

现在再看一遍，你会发现这些修改不是互不相关的补丁：

1. 先选对 FAWA 路径，避免在不适用的 HLA 检查里出问题。
2. 按实际缓存组和共享关系，确定有哪些数据。
3. 区分要保存的结果与需要重建的临时状态，并保留组编号。
4. 按每层压缩比例，把逻辑 token 换算成实际状态。
5. 按真实 layout 找到 value、scale 或完整页，算对地址和长度。
6. 让 scheduler、worker、Store 对记录大小及 key 格式达成一致。
7. 第一次正常计算后，保存已完成、可持久化的数据。
8. 第二次查找时，选择能安全恢复的前缀边界，而不是一味追求更多命中。
9. 写回 GPU 前先等旧写操作完成，写回后等加载完成。
10. 由模型 replay 或续算，恢复未保存的状态。
11. 依据实际计算进度保存新结果，不提前 dump。

任何一个环节不一致，都可能出现“看起来命中了，实际却恢复错了”。

## 14. 为什么说这些修改有依据，又不能说已经覆盖所有情况？

“为什么能解决”可以分成三层理解。

第一层是机制对应。地址错误就按真实布局重算，格式混用就隔离 key，跨流覆盖就补执行顺序，replay 进度错误就使用 scheduler 的真实起点。这些修改各自针对一个明确的不一致。

第二层是单元测试。现有测试检查数值和 scale 的字节往返、压缩偏移、整页大小、组编号、FA-only、恢复边界、replay 保存位置、同步先后顺序，以及 V4 原有行为。

第三层是真实模型验证。你已经反馈临时镜像上的精度问题在修复后解决；这是这个场景的有效证据。但新版 layout、不同 dtype、硬件及并行配置，仍需要相应的实际运行验证。

单元测试通过，不等于完整模型一定通过；某个镜像上精度恢复，也不等于所有版本都无需再验证。本次只是编写解释文档，没有重新跑模型或测试。
